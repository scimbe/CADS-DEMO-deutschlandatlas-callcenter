# Naturalness analysis: why the callcenter still doesn't sound like a conversation

> Follows the format of [`testing-strategy.md`](./testing-strategy.md). Every claim below is backed
> by a specific measurement or a verbatim quote from one real Playwright run against the live
> deployment; none of it is a subjective "it sounds robotic" impression (this analysis has no ears).

## Method

A Playwright script drove the live site (`https://callcenter-34a13a96.bunsenbrenner.org/`, confirmed
on commit `d730736`+ via `/health`/`/fsm`) through 6 turns: one question, three offered-suggestion
clicks, a topic pivot to a new question, one more click. It captured:

- Every JSON response from `/understand`, `/filler`, `/intro`, `/answer`, `/followup`, `/greeting`,
  `/topicack` — 38 calls total.
- Every audio file actually fetched by the browser (24 `.wav`/`tts-stream` clips, saved to disk).
- `play`/`pause`/`ended` events on `#player` (the ordered-queue element) via `page.addInitScript`,
  the exact pattern documented in `testing-strategy.md` §3.

Acoustic measurements used `ffprobe`/`ffmpeg -af volumedetect` / `-af astats` on the saved clips —
the same tools this repo already uses for STT preprocessing (`src/callcenter_speech`).

**Raw data** (all under `/tmp/callcenter-naturalness-audit/`, this machine):
- `run.mjs` — the capture script
- `api-log.json` — all 38 API responses, ordered
- `audio-files.json` / `clips/clip-NNN.wav` — the 24 captured clips, in fetch order
- `audio-events.json` — the `#player` play/pause/ended timeline

**Known methodology limitation**: only `#player` was instrumented, not the separate `#filler`
fallback element (`gui/index.html`'s wait-clip loop). A silent gap on `#player` below may be covered
by that fallback playing underneath it — this analysis cannot tell from `#player` events alone, and
says so explicitly wherever it matters (§3).

## 1. Content that should never reach a text-to-speech engine

**Finding, with exact evidence:** six of the 38 captured responses contain literal German
gender-inclusive double-underscore notation (`Ausländer__innen`, `Hausärzte__ärztinnen`,
`100_000 Einwohner__innen`) — a written/screen-reader convention, not something meant to be *spoken*:

```
/filler:   "Verstanden — Ihre Frage lautet: Wie hoch ist der Anteil der Ausländer__innen an der
            Gesamtbevölkerung in Frankfurt?"
/filler:   "In Ordnung, Ihre Frage ist: Wie viele Hausärzte__ärztinnen gibt es je 100_000
            Einwohner__innen in München?"
/followup: "...interessiert Sie auch, wie hoch der Anteil der Ausländer__innen an der
            Gesamtbevölkerung in Hamburg ist?"
```

This text is generated by the LLM steps in `UNDERSTAND_SYS`/`FOLLOWUP_SYS` (`gui/server.mjs`) and
handed straight to `ttsSpeak()` with only `stripPronunciation()` applied — a function that targets
IPA/pronunciation-guide brackets, not gender notation. Piper/the channel voice has no defined behavior
for a bare `_` character; at best it's a jarring "underscore" stumble, at worst dead air or a synthesis
error. This is a mechanical, unconditional fix: strip/normalize `\w+__\w+` (and the bare `_` in
`100_000`) to natural spoken form before every `ttsSpeak()` call, not just for funfacts.

**Second finding, same category, likely still broken:** `stripPronunciation()` is supposed to remove
bracketed IPA guides, but this funfact survived it verbatim:

```
/filler funfact: "München, das man auf Standarddeutsch oder ausspricht und im Bairischen [ˈmɪŋɐ]
                   sagt, ist die Landeshauptstadt des Freistaates Bayern."
```

Two problems in one sentence: the bracketed IPA `[ˈmɪŋɐ]` should have been stripped (it contains the
`ˈ` stress mark the regex explicitly checks for — worth diffing the exact Unicode codepoints in the
live LLM output against the regex's literal character class, since this is proof the regex is not
matching *something* it should), and the surrounding clause is grammatically broken ("das man auf
Standarddeutsch **oder** ausspricht" — a word is missing between "oder" and "ausspricht", almost
certainly because `narrate()`'s LLM rephrasing step tried to preserve a source sentence that itself
had the IPA guide embedded mid-clause, and mangled it in the process of "keeping every fact exact"
while restyling). **Generic fix, not just a regex patch:** run `stripPronunciation()` on the raw
Wikipedia extract *before* it goes into the `narrate()` prompt, not only after — so the LLM is never
shown IPA notation to begin with and can't reproduce or half-strip it.

## 2. Register whiplash inside a single funfact

```
/filler funfact (Köln): "Köln, die lebendige Metropole im Herzen von Nordrhein-Westfalen, ist mit
                          etwa einer Million Einwohnern nicht nur die größte Stadt des Bundeslandes,
                          sondern auch die viertgrößte Deutschlands."
```

vs., seconds earlier in the *same session*:

```
/filler funfact (Kiel): "Kiel ist die Landeshauptstadt von Schleswig-Holstein und hat mit 251.842
                          Einwohnern (Stand 31. Dezember 2025) die meisten Bewohner im ganzen
                          Bundesland."
```

Both are numerically correct, but "die lebendige Metropole im Herzen von..." is tourism-brochure
copy — a register the rest of the callcenter (data lookups, "Verstanden, Ihre Frage lautet...") never
uses. This is `narrate()`'s `temperature: 0.4` doing exactly what a temperature>0 rephrasing prompt
will do: vary *style* along with wording, with no register anchor to keep it inside. **Generic fix:**
pin the register explicitly in the `narrate()` system prompt for `mode==='funfact'` (e.g. "sachlich,
wie eine Radionachricht, keine Werbe- oder Reisefĥrer-Sprache") rather than only constraining content
fidelity as the current prompt does.

## 3. The same question gets echoed twice, worded two different ways, seconds apart

```
t=1788813716732  /filler verstehen: "Ich sehe, Sie wollen wissen: Wie hoch ist der Ausländeranteil
                                      in Frankfurt?"
t=1788813722185  /filler verstehen: "Verstanden — Ihre Frage lautet: Wie hoch ist der Anteil der
                                      Ausländer__innen an der Gesamtbevölkerung in Frankfurt?"
```

5.4 seconds apart, both labelled `kind:"verstehen"`, both about Frankfurt — but one says "Wie hoch ist
der Ausländeranteil" and the other "Wie hoch ist der Anteil der Ausländer\_\_innen an der
Gesamtbevölkerung", i.e. two different surface forms of the same question, back to back, in the SAME
delivered turn's filler loop. This happens because `/understand` can *reformulate* the caller's
question (`best_guess` differs from the raw text or from a followup suggestion's exact string), and
the speculative filler prefetch in `ask()`/`doFollowup()` is keyed to whichever text was known
*first* — when the resolved text differs, the client (correctly, per `gui/index.html`'s own logic)
discards that prefetch and fires a *fresh* `runFillerLoop()` for the resolved text, but the discarded
prefetch's request had already reached the server and its filler got queued into `#player` too.
**This needs the fix in the app, not just documenting:** either cancel/ignore an in-flight filler
fetch once its query is known to be stale (`AbortController`, keyed by query string), or — simpler,
no networking change — have the client only start the *speculative* filler prefetch it's fairly
confident won't be superseded (e.g. skip the `ask()`-time speculative fetch entirely when the raw
query looks like it will need LLM reformulation, and only ever prefetch once from the resolved text).

## 4. Acoustic evidence of "stitched together": abrupt clip starts, natural clip ends

`ffmpeg -af astats` on the first and last 80ms of two representative clips:

| clip | position | Peak dB | RMS dB |
|---|---|---|---|
| clip-001.wav (4.1s) | start | **0.00** | -13.65 |
| clip-001.wav | end | -21.08 | -33.22 |
| clip-010.wav (12.4s) | start | **-1.74** | -13.38 |
| clip-010.wav | end | -63.86 | -77.21 |

Every clip's **end** decays toward silence naturally (RMS drops 20-60dB in the last 80ms) — that part
is fine. Every clip's **start** is already at (or within 2dB of) full amplitude in the *first* 80ms —
there is no lead-in, no breath, no soft attack. A human speaker's utterance never starts at 0dBFS in
its first 80 milliseconds; this is the single most measurable acoustic signature of "several separately
synthesized clips glued in sequence" rather than one continuous utterance, and it repeats on **every**
clip boundary in the queue (bridge → filler → filler → answer → invite is 4-5 boundaries per turn).

Loudness itself is *not* the problem — checked and ruled out: mean volume across sampled clips is a
tight -14.8 to -16.5 dB with a hard -0.0 dB peak ceiling on every clip, i.e. the TTS backend already
normalizes/limits consistently. The seam is timing (attack), not level.

**Generic fixes compatible with the current architecture** (raw `<audio>` element swap, one clip =
one file, no client-side mixing today):
- Ask for (or apply server-side, once, at save time in `ttsLocalPiper`/`localizeChannelClip`) a short
  linear fade-in (~40-60ms) on every synthesized clip. This is a cheap, one-line `ffmpeg -af
  "afade=t=in:d=0.05"` pass when writing the `.wav` to `TTS_DIR` — no client change needed at all.
- If moving beyond the raw `<audio>`-element-swap architecture is ever on the table: the Web Audio
  API (`AudioContext` + `GainNode` scheduling, decoding each clip via `decodeAudioData` and scheduling
  playback with a few hundred ms of cross-fade between adjacent buffers) removes the seam entirely
  and would also let multiple already-fetched clips be *pre-decoded* while still queued — the natural
  evolution of the buffering work already done in `gui/server.mjs`'s `FILLER_LOOKAHEAD`. This is a
  bigger change (a new playback engine replacing `pump()`/`seq`), so treat the fade-in as the
  immediate fix and Web Audio as the strategic one.

## 5. Large, uneven gaps on the ordered player — buffering isn't keeping the pipe full everywhere

Measured silence between one clip's `ended` and the next clip's `play` on `#player`, this session (ms):
**5787, 7452, 168, 349, 557, 26061, 3135, 150, 11668, 12180.**

The short ones (150-550ms) are exactly what `FILLER_LOOKAHEAD` buffering is supposed to produce —
working as intended there. The four multi-second-to-26-second gaps correlate with `/understand` and
`/followup` calls in the log (`/followup` at `t=1788813770113` and `t=1788813817539` sit right before
the two largest gaps): both routes chain an LLM call, `validateSuggestions()` re-running the live
pipeline for candidate follow-ups, and (for `/followup`) a final `ttsSpeak()` for the invite — none of
that work is covered by the `/filler` `FILLER_LOOKAHEAD` buffer at all, because it isn't a `/filler`
call. **Caveat (see Method):** these gaps are silence on `#player` specifically; the separate
`#filler` fallback loop may (by design) be covering some of this with generic wait-clips — this
capture can't distinguish "26 seconds of true silence" from "26 seconds of fallback filler audio,
which is real content just not the rich contextual kind." Either way, the practical effect is the
same complaint: during exactly the calls that most need bridging (a multi-step `/followup` round
trip), the caller is being handed to the generic six-phrase fallback loop instead of the richer
`/filler` content — the opposite of what the redesign intended.

**Generic fix:** extend the same "keep N requests in flight" buffering principle from `/filler` to
`/followup`'s own internal latency — e.g. have the client start speculatively priming a *generic*
`/filler`-n≥3 clip (cheap, prewarmed, near-instant) the moment it knows a `/followup` call is in
flight and hasn't resolved within ~1-2s, rather than falling through to the static six-phrase
`FILLER_PHRASES` loop, which is the one part of this system with the least variety of all (see §6).

## 6. Variety over a longer conversation — what's actually rotating well, and what isn't

Across the ~10 `verstehen` fillers in this one session, **8 distinct** lead-ins from
`VERSTEHEN_LEADINS` appeared with zero exact repeats: "Klar, es geht Ihnen um", "Ich sehe, Sie wollen
wissen", "Verstanden — Ihre Frage lautet", "Alles klar, Sie möchten wissen", "Gut, Sie fragen", "Ich
habe verstanden — Sie möchten wissen", "In Ordnung, Ihre Frage ist", "Notiert — Sie interessiert".
`rotFor()`'s per-caller rotation (`gui/server.mjs`) is doing exactly what it was built to do — this
part of the September rework is confirmed working, not a source of the "geringe Streuung" complaint.

What *is* thin over a longer session:
- **The fallback filler loop is only 6 static phrases** (`FILLER_PHRASES` in `gui/server.mjs`,
  played from pre-rendered `.wav` files) — see §5, this is exactly what plays during the longest,
  most noticeable gaps, so its low variety is disproportionately audible.
- **Funfact register drifts per-city with no shared voice** (§2) — "high variety" in wording that
  isn't anchored to one consistent style reads as *inconsistency*, not liveliness; breadth and
  register-consistency are not the same axis and both need to hold simultaneously for "natural".
- **The `EX_POOL` static example bubbles and live `/followup` suggestion bubbles render into the
  identical `#examples` DOM container with the identical `.ex` class** (`gui/index.html`), with no
  visual or semantic distinction between "a generic starter example" and "a suggestion that actually
  follows from what you just heard". This capture cannot prove a real caller ever confuses the two
  (this script's own bubble-selection logic could not reliably tell them apart either, which is itself
  the point), but it means nothing in the DOM/architecture *prevents* a stale or generic suggestion
  from standing in for a contextual one — worth a `data-source="example"` vs `"followup"` marker at
  minimum so this is at least verifiable, if not preventable.

## Prioritized, minimal-change recommendation

1. **Strip gender-inclusive `__` notation (and normalize bare `_`) before every `ttsSpeak()` call** —
   §1, unconditional correctness fix, cheapest and highest-impact item here.
2. **Run `stripPronunciation()` on the Wikipedia extract *before* it enters the `narrate()` prompt**,
   not only on `narrate()`'s output — §1, closes the specific München leak and prevents the LLM from
   ever seeing IPA notation to mangle.
3. **Add a ~50ms fade-in when a clip is saved to `TTS_DIR`** (one `ffmpeg` flag in
   `ttsLocalPiper`/`localizeChannelClip`) — §4, the single biggest acoustic "stitched" signature, fixed
   with no client or protocol change.
4. **Pin funfact register in the `narrate()` prompt** ("sachlich, kein Werbe-/Reiseführer-Ton") — §2.
5. **Stop a stale speculative filler prefetch from still being queued after its query was
   superseded** — §3, needs either `AbortController`-based cancellation keyed by query, or narrowing
   when the speculative prefetch fires at all.
6. **Widen `FILLER_PHRASES` (currently 6) and/or bridge `/followup`'s own latency with a
   `/filler` n≥3 call instead of falling through to it** — §5/§6, addresses the least-varied, most
   audible part of the whole system precisely because it plays during the longest waits.
7. **Mark example vs. follow-up bubbles distinctly in the DOM** — §6, cheap, makes a real discourse-
   coherence question actually verifiable going forward instead of only inferable from logs.

Items 1-4 are single-function, no-architecture-change fixes. Items 5-7 touch the client/server
protocol slightly (a query-id for cancellation, a fallback wiring change, a DOM attribute) but stay
inside the existing design (stateless server, client-owned ordered queue, single-slot TTS channel).
